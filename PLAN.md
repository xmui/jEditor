# jEditor: plan

## What jEditor is

**Three apps in one, and easy to use.** jEditor is:

1. **A simple, handy photo viewer and editor**, like Preview on the Mac: open a folder, look, rotate, crop, flag, rename, move on. This is the home screen and it stays fast and uncluttered.
2. **A photo editor like Lightroom** (Adjust): light, colour, looks, masks, spot removal, done non-destructively.
3. **A Photoshop/Paint app** (Paint): layers, brushes, shapes, text, images brought in, new canvases.

The three are modes of one app (Photos, Adjust, Paint), switched in one place. **What matters most is that it's intuitive and there's never too much on the screen:** each mode shows only what it needs, extra controls live in menus and right-click menus rather than on toolbars, and every new feature has to fit without adding clutter. When in doubt, show less.

## One jEditor: Windows, Mac and web

jEditor is one product, in this repo, shipped three ways from one UI (`app/`):

1. **Windows**: the full app, as it is. Nothing is taken away.
2. **Mac**: an installed app with the core workflow, native file access (no permission prompts) and folders opened from Finder.
3. **Web**: back at https://xmui.github.io/jEditor/, the core workflow in Chrome or Edge.

**The core** is what every platform has: open a folder, view, rotate, crop and straighten, flags, search, rename, move, delete with undo, export, duplicates, Auto crop and watching the folder. That's the last web version's features (1.18.1) and everything since that isn't tied to Windows. Hardware and Windows-integration features (scanning, camera tethering, Explorer's pins, the Recycle Bin) stay Windows-only for now; their Mac equivalents are on the back burner.

### Decisions

- **One repo, xmui/jEditor.** The Windows app lived in xmui/jeditor-windows from 1.18.1 to 1.35.1. Its history already contained all of jEditor's, so it came back with nothing lost. Installed copies from before 1.35.1 look for updates only there, so 1.35.1 (released in both) checks both repos and takes the newest; jeditor-windows is archived once the lab PC has it, with its releases kept.
- **Windows stays .NET 8 + WebView2.** Scanning (NAPS2), the 32-bit TWAIN helper, tethering, the Recycle Bin and the updater are C# and work; no rewrite.
- **Mac is Electron.** The UI edits files through the File System Access API, which only Chromium has (Safari's WebKit doesn't), so Electron runs the UI exactly as WebView2 does and one test suite covers both. Its host gives the page folder handles backed by the disk by path (through its preload script), as the Windows host does with `CreateWebFileSystemDirectoryHandle`, so there are no prompts and folders open from Finder or a path. Cost: a ~150 MB app.
- **The web is `app/` as it is,** with no host: `window.JEditorNative` is `null`, as in the UI tests. The site is built from the latest UI, not 1.18.1, at the same address, so people's settings and recent folders carry over.
- **Hosts say what they can do.** Today the UI asks "is there a host?" and then assumes Windows. Each host will list its features (`scan`, `trash`, `windows`, `places`, `updates`, …) and the UI checks each one, so the Mac app never shows a Scan button that does nothing. The tests run the UI with no host, the Windows host and the Mac host.
- **One version, one changelog, one release:** the Windows setup and zip, the Mac `.dmg`, `standalone.html`, and the site deployed from the same commit.
- **Layout, later:** `app/` (the UI), `hosts/windows/` (today's `src/`, `twain32/`, `installer/`), `hosts/mac/`, `test/`, `scripts/`, `docs/`. Moved in its own PR, with nothing else in it.

### Phases

1. **Consolidate (1.35.1).** The Windows app's history comes back here; CI and releases run here; the updater checks both repos. *Then:* archive xmui/jeditor-windows once the lab PC is on 1.35.1. New work starts from this repo.
2. **Capabilities, then the web (1.36.0).** Apps list their features and the UI checks them (`app/host.js`, with tests for no app, the Windows app and a core-only app). The Web app workflow deploys the latest UI to Pages on every push to `main`, once the tests pass, and each release attaches `standalone.html`. Checked: a browser that used the 1.18.1 site keeps its settings, recent folders, sort order and flags on the new one.
3. **Mac app, core (1.37.0).** Electron in `mac/`. A folder handle for any path: the app drops the folder onto the page over the DevTools protocol (`Input.dispatchDragEvent`), Chromium gives the page a real `FileSystemDirectoryHandle`, as for a folder dragged in from Finder, and the permission check grants it without asking. So no handle polyfill: files read lazily from disk, `FileSystemObserver` works, handles go into IndexedDB (Recent). The Mac's folder picker, Finder's Open With and the Dock, Recent and Stored projects by path, Show in Finder, the title bar following the theme. Projects' data in the app's private storage (OPFS), so no `.jeditor` and nothing in `~/Library` for Chromium to refuse. Deleting uses jEditor's trash (Ctrl+Z restores). `test/mac.test.js` drives the real app (Linux under xvfb, and macOS); CI builds an ad-hoc-signed universal `.dmg` on a Mac and smoke-tests the built app; releases attach it.
4. **Mac extras (1.38.0, done but for the Trash).** The projects sidebar (`/Volumes`, Eject), several windows and Split, the update check (download the new .dmg; installing it in place needs signing). Deleting to the Trash with Ctrl+Z bringing it back: `NSFileManager.trashItem` gives where it went (through `osascript`), but taking it out again may need Full Disk Access, so try on a Mac first. Messages that say "Ctrl+Z" should say "⌘Z" there (the keys already work; only the wording).

5. **Liquid Glass on the Mac (1.38.0; native in 1.39.0).** On macOS 26 the top row is a native NSToolbar (`mac/native`), which the system draws in real Liquid Glass; its items mirror the page's controls, so their behaviour stays the page's. Electron has no glass API (its PR was closed unmerged), and a native view above the page would cover the page's own buttons, so the rest (bottom bars, the folder panel, menus) keeps the CSS glass below, as does macOS before 26. Homebrew: this repo is a tap (`Casks/jeditor.rb`), updated by each release; Homebrew's own casks need signing.
   *1.38.0's CSS glass, as first written:* Glass on the controls, never on the photos: the photos and the surround stay solid in the colour chosen, so judging colour isn't thrown off. The window's title bar goes, its traffic lights sitting in jEditor's own toolbar, which floats over the content as macOS 26's do. The Mac's own window material shows through the start screen; the folder panel floats over the photos, so it's glass over them, not the desktop. The floating pills (toolbar, selection bar, the controls over the film strip, messages) get a refined glass: a soft blur, a fine highlight along the top edge, a little refraction at the edges, darkening (or lightening) what's under it so text keeps its contrast over any photo (measured in the tests: 7:1 for text, at least 4.5:1 for secondary text, over pure white and pure black). No refraction: it would bend the photo under the toolbar. Calm, short transitions; text always readable. Reduce Transparency and Increase Contrast make it solid, and the Glass setting gains Off. Checked with screenshots on light, dark and busy photos, and tests that glass never covers a photo and turns solid with Reduce Transparency.
6. **Linux (1.40.0).** The Mac app's Electron host (`mac/`) with `platform: 'linux'`: Linux's words (Files, this computer; Ctrl stays Ctrl), drives from `/proc/mounts` under `/media/<user>`, `/run/media/<user>` and `/media`, plus the computer's own disk, ejected with `gio mount -e` or `udisksctl`; a menu bar shown with Alt. Packaged as an x64 AppImage (updates itself: the new one is checked, written over `$APPIMAGE` and relaunched), a .deb and a pacman package for Arch (no self-update: apt or pacman). CI runs `test/mac.test.js` on Linux as both apps, builds all three, smoke-tests the build, installs and removes the .deb, and does the same with the pacman package in an `archlinux` container. An AUR package (`jeditor-bin`, from the release's .pacman or AppImage) needs an AUR account: the owner's to set up. Still to do: deleting to the freedesktop Trash (jEditor's trash for now), arm64 builds, a Flatpak.
7. **iOS (iPad first), later.** Every iOS app must use Safari's WebKit, which has no File System Access API, so Electron and the web app's file code can't run there. It needs a native Swift layer for files (the Files app's folders: iCloud Drive, USB drives, SMB shares through security-scoped bookmarks, and the Photos library) with the UI in a WKWebView on top, and the file layer bridged to it. The workflow is rethought around where photos are on an iPad. Needs the Apple Developer account (as Mac signing does) and the App Store or TestFlight. iPad first: reviewing a scan order fits its screen.

**Known on the Mac (and Linux):** a photo restored from jEditor's trash comes back with permissions 600 (owner only), as Chromium makes new files; edits keep a photo's permissions.

**Before the Mac app goes to customers:** an Apple Developer account ($99 a year), to sign and notarize it. Unsigned, macOS says it "can't be opened" and people have to find Open Anyway in System Settings → Privacy & Security; an unsigned app also can't update itself, only download the new `.dmg`. Adding signing changes CI, not the app.

**Back burner:** scanning on the Mac (Apple's ImageCaptureCore; the FastFoto has Mac drivers), tethering on the Mac, anything hardware-related on the web.

## Roadmap (set 2026-10-17)

**Rules for everything below.** Windows first: each feature is made the best it can be in the Windows app, then brought to the Mac, Linux and the web as well as each allows. The basic workflow (open a folder, look, rotate, crop, flag, move on) stays fast and responsive: a new feature never slows it, and the tests time it.

Rotate and crop keep working as they do. Levels and curves with a live histogram, white balance, exposure, contrast, highlights and shadows, HSL and colour grading, sharpening and noise, masks (brush, gradient, and later subject), spot and dust removal, filters and film simulations, presets, copy and paste settings, before and after. Processing on the GPU (WebGL2/WebGPU) so sliders stay live. RAW comes after: first the embedded preview, then full RAW editing.
   - **Released in 1.42.0 as an experiment** (Settings → Experimental; on to start with in betas, `Experiments.LIST` `beta: true`), until it's been used on real orders. **Part of jEditor from 1.45.0**, no longer an experiment.

Light (exposure, contrast, highlights, shadows, whites, blacks), Color (temperature, tint, vibrance, saturation), levels on a live histogram (all channels or one), a point curve (RGB, R, G, B), the color mixer (hue, saturation and luminance of eight colours), Auto and Auto color (per-channel levels: the cast off a faded print), before and after, copy and paste onto a selection, Done & next. `app/develop.js` turns the settings into two lookup tables (per channel, and a 33³ colour table), applied with WebGL2, or the same tables on the CPU without it, so there's one definition of every slider. Kept as `adj` on the photo's edit in `.jeditor/edits.json`, always (an adjusted photo's crops and turns are kept with it), shown in the viewer, thumbnails and the crop editor, written by Export and Save edits. Without a project, Done writes the photo.
   - **Second step (1.42.0 beta 2):** colour grading (three wheels, blending, balance) in the colour table; Looks (34 film simulations of real stocks in `Develop.LOOKS`, grouped by process: C-41, E-6, ECN-2, B&W and creative; each its own `adj` applied over the photo's with an Amount, shown as thumbnails of the photo; B&W films convert with their own red/green/blue sensitivity on linear light (`mono`); CineStill's halation is a glow map, the highlights of a 320-pixel copy of the whole picture blurred, sampled by position on the GPU and the CPU alike; colour films' grain is partly per channel, as dye clouds) and user presets (saved `adj`s, in the browser's storage); Effects (vignette and grain) as a stage of their own in the shader after the tables, with the same maths and noise hash on the CPU, placed by where the pixel is in the whole picture so tiles and preview sizes agree.
   - **Third step (1.42.0 beta 3): Detail.** Sharpening (unsharp mask on brightness, with radius and edge masking) and noise reduction (an edge-keeping bilateral blur of brightness, a blur of colour), in brightness/colour (Y, Cb, Cr), separable passes, on the photo before the tables. On the CPU (`Develop.applyDetail`), in blocks read with a margin so they match the whole picture; sizes are in the photo's own pixels, so screen-sized previews (under half size) leave it out and the panel has a 1:1 view from the full photo. Export at 24 MP with everything on takes a few seconds: a worker or a GPU version later if that's felt.
   - **Fourth step (1.42.0 beta 4): Masks.** Linear and radial gradients and a brush (paint and erase, size, feather, flow), each with its own exposure, contrast, tones, white balance, vibrance and saturation; up to eight. Kept in the photo's own coordinates (before crop and turn; `Develop.cropMap` maps the picture shown to them), so a later crop doesn't move them. On the GPU: each mask has a row of the channel table and a slab of a 17³ colour table, its shape from uniforms (gradients) or a brush map (two RGBA maps, a channel per brush mask, the photo's long side 512, painted with the canvas); the CPU does the same. Subject and sky masks (AI) later.
   - **Fifth step (1.44.0 beta): Spot removal.** Heal and clone circles (`adj.spots`), placed on the photo as it is on disk and done on the whole photo before the crop (`app/retouch.js`), so every size of it (thumbnail, preview, full) gets the same and a crop later doesn't move them. Heal spreads the difference between the spot's edge and its source's smoothly over the inside (a membrane, relaxed on a grid of up to 40 cells). A click sizes the spot to the speck under it and picks the source where the ring round it matches best; Find dust looks for small dots much darker or lighter than what's round them, on smooth ground, and puts a heal spot on each (`d: 1`, so Clear found takes them off). Adjust keeps the uncropped working copy, and the spots done but the last, so adding one or dragging one is quick. Copy/paste and presets leave a photo's spots behind.
   - **Sixth step (1.44.0 beta): Sky and Subject masks** (`app/select.js`), found from colour, brightness, texture and sharpness (no model to run in the browser): the sky grown from smooth bright or blue ground along the top until an edge, and through gaps, its edge refined by colour; the subject what stands out from the frame's edge colours and is sharper than the background, the middle counting more, refined by k-means colours in and out. Kept as a run-length coded 16-level map (256 px) with the mask and drawn into a brush-map channel, so the GPU and CPU paths are unchanged; brush strokes touch them up.
   - **RAW (1.44.0 beta), first step:** shown and edited from the embedded full-size JPEG (`app/raw.js`: TIFF IFDs/SubIFDs/EXIF, CR3's first track and PRVW, RAF's header; a DNG's lossless raw data is never taken), oriented as the RAW says. A RAW is never written: its edits are always kept, Export and Save edits write JPEG copies.

## The Windows app


### Why a Windows app, and why it can work without admin

The lab has one Windows PC (an Epson FastFoto FF-680W and a Plustek OpticBook A300). The web app worked there but had limits a browser can't get past: permission prompts, no way to look up from a folder to its order, a `.jeditor` folder that isn't really hidden, no Recycle Bin, and no scanning. See "Native Windows app and in-app scanning" in [docs/jeditor-plan.md](docs/jeditor-plan.md) for the full list, and the lab's scanners.

**Lab PC test (2026-10-12):** MultiMC, an unsigned portable .exe, ran from the user's own folder without admin. So nothing on that PC blocks unsigned apps run from user folders (no AppLocker rule, no Smart App Control). A per-user install of jEditor runs there too. Expect at most a one-time SmartScreen "More info → Run anyway", since a new app has no reputation yet.

### How it's built

- **.NET 8 WinForms + WebView2.** Not Tauri, and not a rewrite of jEditor's ~12.6k lines. WebView2 is Edge's engine, so jEditor runs as it does in Edge. The deciding feature is `CoreWebView2Environment.CreateWebFileSystemDirectoryHandle` (stable since WebView2 SDK 1.0.2651.64; pinned at 1.0.4258.31): the app makes a real `FileSystemDirectoryHandle` for any path, with edit permission already granted, and posts it to the page. jEditor's File System Access code then works unchanged, with no permission prompts. C# also has NTwain for TWAIN scanning, and easy access to the Recycle Bin, Explorer's thumbnails and the rest of Windows.
- **One repo.** It started in xmui/jeditor-windows with jEditor (the web app, xmui/jEditor) as a submodule; on 2026-10-12 the UI moved in, with its history, and the web app was retired; at 1.35.1 the whole thing came back to xmui/jEditor (above). Its old plan is in [docs/jeditor-plan.md](docs/jeditor-plan.md). The UI is still standard web code: `src/bridge.js` runs before it and replaces `showDirectoryPicker`. The bridge relies on the `app` object (`openDirectory`, `files`, `rotateImage`, `isLoading`) for opening a folder from the command line and for the smoke test, and on `data-theme` on `<html>` for the title bar. The UI's tests (`test/ui.test.js`) still run it in Chrome.
- **The UI ships as files.** The `app` folder sits beside the exe, so a UI change never needs a rebuild. `--ui <folder>` runs the UI from a checkout in dev mode, where CSS changes show live.
- **No admin anywhere.** It's a self-contained exe, because a shared .NET runtime would need admin to install. The installer is Inno Setup with `PrivilegesRequired=lowest`: `%LOCALAPPDATA%\Programs\jEditor`, the user's Start menu, and the uninstall entry in HKCU. CI checks nothing lands in Program Files or HKLM.
- **Origin `https://jeditor.example/`, fixed.** IndexedDB and localStorage (settings, recent orders, the flags cache) are stored under it.

### Phases

### Things WebView2 might do differently from Chrome

Check these on the lab PC:

- Dragging a folder in: WebView2 should hand over a folder handle, as Chrome does, and the app allows editing it without a prompt.
- Watching the folder: jEditor uses `FileSystemObserver` where it exists and checks every so often otherwise. Which one runs in WebView2 depends on the Edge version installed. Either way photos from the scanner show up, just less instantly with polling.
- Recent orders after a restart: the stored handles need permission again, which the app grants without asking.
